# Authoring OKF Bundles (v0.2)

OKF represents knowledge as a **bundle**: a directory of markdown files with YAML frontmatter. One file = one **concept**. The file path minus `.md` is the concept's identity, so paths must stay stable.

Every fact below is labeled. **[SPEC]** = normative in OKF v0.2 (`GoogleCloudPlatform/knowledge-catalog`, `okf/SPEC.md`). **[PRACTICE]** = community convention; useful, not binding. Do not present a [PRACTICE] rule to the user as a spec requirement.

## Frontmatter reference

[SPEC] Exactly one field is required: `type`. A concept carrying just `type` is fully conformant. All other fields are optional; consumers MUST NOT reject unknown keys.

| Field | Status [SPEC] | Shape |
|---|---|---|
| `type` | required | short string; not centrally registered — pick a meaningful name (`Table`, `Metric`, `Runbook`), never a generic `concept` |
| `title` | recommended | human-readable name |
| `description` | recommended | one sentence, used for previews and index entries |
| `resource` | recommended | canonical URI of the underlying asset; omit for abstract concepts |
| `tags` | recommended | YAML list of strings |
| `generated` | optional | `{ by: <actor>, at: <ISO 8601> }` — who/what produced this |
| `verified` | optional | list of `{ by: <actor>, at: <ISO 8601> }`; a bare mapping is read as a one-element list |
| `status` | optional | `draft` \| `stable` \| `deprecated` — closed set, defaults to `stable`. `reviewed` is not a value; a review is a `verified` entry |
| `stale_after` | optional | ISO 8601 timestamp after which the concept needs re-verification |
| `sources` | optional | list of `{ id, resource, title?, author? }` — external material this concept derives from |

[SPEC] Actor strings: `<producer>/<version>` for agents and tools (`schema-pipeline/1.2`), `human:<id>` for a person (`human:alice`), `process:<id>` for automation. The `human:` prefix is what consumers key trust on — hand-authored or human-confirmed content MUST use it.

[SPEC] Trust tiers derived by consumers: no `verified` ⇒ unverified; `verified` by non-`human:` actors only ⇒ machine-confirmed; any `verified` entry with a `human:` actor ⇒ human-reviewed.

[PRACTICE] Fill `generated` even though it is optional — provenance is the first thing a consumer asks for.

## Reserved filenames

[SPEC] `index.md` and `log.md` are reserved at every directory level and MUST NOT be used for concept documents. Do not invent alternatives (`index.yaml`, `changelog.yaml`, `manifest.json` are all wrong).

**`index.md`** — [SPEC] enumerates the directory's contents for progressive disclosure. No frontmatter, with one exception: the bundle-root `index.md` MAY declare `okf_version: "0.2"`. Entry format:

```markdown
# Tables

* [Orders](/tables/orders.md) - One row per customer order; feeds GMV.
```

[PRACTICE] Write each entry as "title - short description", reusing the concept's `description` field, so an agent can choose what to open without reading everything.

**`log.md`** — [SPEC] flat list of date-grouped entries, newest first, ISO `YYYY-MM-DD` headings:

```markdown
# Update Log

## 2026-08-27
* **Creation**: Added [Orders](/tables/orders.md).
```

## Links and citations

[SPEC] Two link forms: absolute bundle-relative (`/metrics/gmv.md`, resolved from bundle root) and standard relative. Absolute is recommended — it survives file moves. [SPEC] A broken link is not malformed; consumers tolerate it.

[SPEC] Per-claim attribution uses markdown footnotes whose label is a `sources[].id`:

```markdown
---
type: Table
sources:
  - id: orders-wiki
    resource: https://wiki.example.com/orders
---
The table is retained for 7 years.[^orders-wiki]

[^orders-wiki]: Orders — internal wiki
```

[SPEC] v0.1 used a body `# Citations` list and a `timestamp` field; v0.2 replaced them with `sources` and `generated`. Migrate on touch; never author new concepts in v0.1 form.

## Worked example

A concept at `tables/orders.md`, generated by a pipeline and reviewed by alice:

```markdown
---
type: Table
title: orders
description: One row per customer order; totals feed GMV.
resource: postgres://prod/shop/orders
tags: [postgresql, sales]
generated: { by: schema-pipeline/1.0, at: 2026-08-01T00:00:00Z }
verified:
  - { by: human:alice, at: 2026-08-05T09:00:00Z }
sources:
  - id: orders-wiki
    resource: https://wiki.example.com/orders
---

# Schema

| Column | Type | Meaning |
|---|---|---|
| id | bigint | Primary key |
| customer_id | bigint | Customer who placed the order |
| total_cents | integer | Order total in cents |
| created_at | timestamptz | Row creation time |

Totals roll up into [GMV](/metrics/gmv.md).[^orders-wiki]

[^orders-wiki]: Orders — internal wiki
```

Adding a concept always means three edits: the concept file, its `index.md` entry, and a `log.md` entry.

## Authoring conventions

- [PRACTICE] One concept per file; each file covers exactly one thing.
- [PRACTICE] Real, varied `type` values and real cross-links — a bundle where everything is one generic type is conformant but useless.
- [PRACTICE] A small, well-typed, hand-checked bundle beats a large auto-generated one.
- [PRACTICE] Never duplicate a fact across concepts; link to the owning concept instead.
- [PRACTICE] Group directories by concept type (`tables/`, `metrics/`, `runbooks/`, `glossary/`).
- [PRACTICE] Keep the bundle in git; the path is the identity, so renames break the graph and history is the audit trail.
- [SPEC] Prefer structural markdown (headings, tables, lists, fenced code) over free prose in bodies.

## Validation before commit

[SPEC §11] A bundle is conformant iff:

1. Every non-reserved `.md` file has a parseable YAML frontmatter block.
2. Every frontmatter block has a non-empty `type`.
3. `index.md` / `log.md` follow the structures above where present.

Nothing else may fail validation — missing optional fields, unknown types, unknown keys, broken links, and missing `index.md` are all tolerated by consumers. Check the three rules with Read/Grep over the bundle; no external validator is needed.

## Common mistakes

| Mistake | Fix |
|---|---|
| Authoring from memory | OKF postdates model knowledge; follow this skill or the spec, never recall |
| `index.yaml` / `changelog.yaml` / manifest files | The reserved files are `index.md` and `log.md`, markdown only |
| `type: concept` | Use a meaningful type naming what the thing is |
| `status: reviewed` or other invented values | `status` is `draft`/`stable`/`deprecated`; reviews go in `verified` |
| Custom `provenance:` block | Use `generated` + `verified` with actor strings |
| `by: alice` for a person | `by: human:alice` — the prefix drives trust classification |
| Relative links by default | Prefer `/path/from/root.md` |
| `# Citations` body section or `timestamp` field | v0.1 forms; use `sources` + footnotes and `generated` |
| Concept file without index/log updates | Every concept change is three edits |
